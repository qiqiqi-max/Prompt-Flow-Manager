1. 先定需求和边界
在让 Agent 写代码前，先产出一页简明规格：
- 功能范围和明确的非目标
- 领域对象、状态流转和不变量
- 角色—资源—操作权限矩阵
- 错误码、分页、排序、幂等语义
- 数据保留、审计、隐私和合规要求
- 性能目标：QPS、延迟、并发量、数据规模
这一步最好由人主导，Agent 负责整理、补充遗漏和提出问题，而不是自行猜需求。
2. 先做设计审查，再生成模板
让 Agent 生成初稿时，输入应包括：
- 数据库 ER 图和字段约束
- OpenAPI/接口契约
- 事务边界和并发策略
- 权限矩阵
- 统一异常与日志规范
然后人工检查关键设计：
- 是否存在越权访问（IDOR/BOLA）
- 是否有 SQL 注入、批量赋值、字段泄漏
- 删除是否应软删，是否需要审计
- 唯一约束、外键、索引是否完整
- 多步写操作是否在同一事务
- 并发更新采用乐观锁、悲观锁还是幂等键
- 分页是否稳定，排序字段是否有索引
- 数据库迁移能否回滚、是否会锁表
不要只审查生成的代码，接口和表结构本身也要审查。
3. 以“一个纵向切片”代替一次生成整套 CRUD
推荐顺序：
1. Migration 和约束
2. OpenAPI 契约
3. 权限策略
4. Service 层业务规则
5. Repository/SQL
6. Controller/DTO
7. 单元测试和集成测试
8. 文档和示例
先完成一个真实业务链路，例如“创建订单→查询订单→修改状态”，跑通后再复制模式。这样比一次性生成几十个接口更容易发现架构问题。
4. 测试采用分层策略
Agent 很适合辅助补测试，但测试场景应由人定义。
至少覆盖：
- 正常路径和边界值
- 未登录、无权限、跨租户访问
- 重复请求和重试
- 并发更新、事务回滚、死锁重试
- SQL 空结果、大数据量分页
- 恶意输入和敏感字段泄漏
- 数据库迁移的升级与回滚
建议测试分层：
- 单元测试：纯业务规则
- Repository/SQL 集成测试：真实数据库或兼容环境
- API 契约测试：请求、响应、错误码
- 安全回归测试：权限和注入
- 少量端到端测试：关键主流程
不要让 Agent 只根据实现反推测试，否则很容易“测试和代码一起错”。
5. 把审查变成自动化门禁
每个 PR 至少自动执行：
- 格式化、静态检查、类型检查
- 单元测试和集成测试
- SAST、依赖漏洞扫描、Secret 扫描
- 数据库迁移校验
- OpenAPI 与实现的一致性检查
- 覆盖率阈值和关键路径覆盖率
- 性能基准或慢查询检查
AI 生成的代码默认进入“待审状态”，不能因为测试通过就自动合并。测试只能证明已覆盖的行为，不能证明权限设计正确。
6. 人和 Agent 的职责边界
比较稳妥的分工是：
Agent 擅长：
- CRUD 样板、DTO、Mapper、SQL 初稿
- OpenAPI、README、测试数据
- 重复性重构和报错定位
- 补充边界测试、生成审查清单
人必须把关：
- 需求和领域模型
- 权限模型、租户隔离、数据分级
- 事务边界和并发语义
- 分布式一致性、消息可靠性
- 迁移、回滚和兼容策略
- 生产发布、监控和应急方案
一句话：Agent 可以提速“怎么实现”，但不能替你决定“应该实现什么”和“失败时必须保证什么”。
7. 上线前后的闭环
上线前定义清晰的 DoD：
- 代码、测试、接口文档、迁移脚本一起提交
- 权限矩阵有对应测试
- 关键 SQL 有执行计划或索引验证
- 有日志、指标、trace 和告警
- 有灰度、回滚和数据修复方案
- 变更经过人工审查并记录决策
上线后收集：
- 错误率、P95/P99 延迟
- 慢查询、锁等待、连接池耗尽
- 权限拒绝和异常访问
- 重试、重复写入、数据不一致
- 用户反馈和线上事故
再把这些问题沉淀为回归测试和编码规范，形成闭环。
可以把整个流程压缩成这条主线：
需求规格 → 威胁建模 → 接口/数据设计 → AI 生成纵向切片 → 人工审查 → 分层测试 → CI 门禁 → 灰度发布 → 监控复盘。

我的工作流：先由人工明确需求边界、数据模型、权限矩阵、事务与并发规则，再让 Agent 生成 CRUD 模板、SQL、接口文档和测试初稿；之后人工重点审核业务逻辑、权限越界、数据隔离、并发一致性、事务边界和数据库迁移风险，重构不合理设计；再借助 Agent 补充单元测试、集成测试、异常处理和问题排查，并通过 CI 做格式检查、静态扫描、漏洞检测和自动化测试。重复性代码和文档交给 AI，需求建模、核心业务、分布式逻辑、安全决策和上线验收由自己把关，最后结合灰度发布、监控告警和线上复盘持续完善，兼顾开发效率、系统安全与代码质量。
